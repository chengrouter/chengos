# ChengOS Skill Package Format — Version 1 (Package v1)

> Status: Active
> Contract consumers: `skill-registry` (server-side validation) and `chengflow`
> (local install-time validation). Both validators MUST implement this document
> independently and MUST report the stable error codes defined in §9.
>
> Compatibility rule: changes to this document MUST be backward-compatible for
> already-published Package v1 artifacts. Breaking layout or semantic changes
> require a new `format_version` and a new spec document (`package-v2.md`).

## 1. Overview

A Skill Package is a single ZIP archive containing one skill. The archive is
content-addressed: its identity is the SHA-256 digest of the archive bytes.
Published artifacts, their manifests, and their digests are immutable.

Artifact media type:

```
application/vnd.chengos.skill-package.v1+zip
```

The package identity used everywhere (publish, catalog, install) is:

```
registry_id + publisher + slug + version + sha256_digest
```

User input never determines where artifact bytes are stored. Storage keys are
derived from the digest only.

## 2. Archive Layout

All paths are relative, `/`-separated, NFC-normalized UTF-8. Exactly one skill
per archive; package files live at the archive root (no wrapping directory).

### 2.1 Required files

| Path            | Type          | Meaning                                                        |
| --------------- | ------------- | -------------------------------------------------------------- |
| `SKILL.md`      | UTF-8 Markdown| Human/LLM-facing skill instructions.                            |
| `skill.yaml`    | UTF-8 YAML    | Canonical skill spec (`CanonicalSkillSpec`, `schema_version: 1`)|
| `manifest.json` | UTF-8 JSON    | Generated package manifest. See §4 and `manifest-v1.schema.json`|

### 2.2 Optional files

| Path             | Type         | Meaning                                                       |
| ---------------- | ------------ | ------------------------------------------------------------- |
| `workflow.json`  | UTF-8 JSON   | Workflow definition for `backend.type: workflow` skills.      |
| `references/**`  | any declared | Reference material (docs, examples, small data files).       |
| `scripts/**`     | UTF-8 text   | Declared text scripts. Every script MUST be declared (§5).    |

### 2.3 Rejected content

A validator MUST reject the whole package when the archive contains any of:

- absolute entry paths, drive letters, or `\` path separators
- `.` / `..` path segments (path traversal)
- duplicate entry paths, or paths that collide after NFC Unicode
  normalization or ASCII case folding
- symlinks, hardlinks, device nodes, FIFOs, sockets
- nested archives (`.zip`, `.tar`, `.tar.gz`, `.tgz`, `.7z`, `.rar`, `.jar`,
  `.gz`, `.bz2`, `.xz`, `.zst`) anywhere in the package
- unknown root files or unknown root directories (anything not listed in
  §2.1/§2.2)
- empty directories carrying metadata (directory entries are ignored;
  only file entries matter)
- native binaries, bytecode, or dynamic libraries anywhere (§6)
- invalid UTF-8 in any file that this spec requires to be text
- archive-bomb characteristics (limits in §7)

Executable permission bits inside the archive are NOT trusted and NOT
preserved. ChengFlow decides final on-disk permissions locally.

## 3. `skill.yaml` requirements

`skill.yaml` MUST parse as YAML and MUST contain at least:

- `schema_version: "1"`
- `name` — the skill slug; MUST equal manifest `slug` and the release slug
- `version` — SemVer 2.0.0; MUST equal manifest `version` and release version
- `description`
- `backend.type` — one of `workflow`, `cli`, `agentic`, `reference`

Additional keys follow the ChengFlow `CanonicalSkillSpec` contract. The
Registry does not execute skills and validates only structural consistency;
ChengFlow performs full `CanonicalSkillSpec` validation locally at install.

Packages MUST NOT contain (validators MUST reject or strip-and-flag):

- credential values or credential bindings
- workspace identifiers, user identifiers
- local enablement, approval, or review state
- runtime logs or execution traces

Slug rule (shared with the Registry): `^[a-z0-9][a-z0-9-]{1,63}$`, no leading
or trailing `-`, no `--` runs required but allowed, max 64 chars.

Publisher handle rule: `^[a-z0-9][a-z0-9-]{1,38}$` (max 39 chars, GitHub-like).

## 4. `manifest.json`

`manifest.json` is generated by publish tooling (never hand-edited), validated
against `manifest-v1.schema.json`, and MUST be consistent with the archive:

- `format_version` MUST be `1`.
- `slug` and `version` MUST match `skill.yaml` and the publish request.
- `files[]` MUST list every file entry in the archive **except
  `manifest.json` itself**, each with `path`, `size` (bytes of the
  uncompressed file), `sha256` (lowercase hex of the uncompressed file), and
  `kind`.
- `kind` is one of: `skill_md`, `skill_yaml`, `workflow_json`, `reference`,
  `script`.
- `scripts[]` MUST declare every file under `scripts/**` (§5) and MUST NOT
  declare paths that do not exist in the archive.
- `compatibility.minimum_chengos_version` is required SemVer;
  `compatibility.maximum_chengos_version` is optional SemVer and, when
  present, MUST be `>= minimum_chengos_version`.
- `dependencies` MUST be present and MUST be an empty array in Package v1.
  Non-empty dependencies are rejected with `PKG_DEPENDENCIES_UNSUPPORTED`
  (field reserved for a future format revision).
- `artifact.media_type` MUST be
  `application/vnd.chengos.skill-package.v1+zip`.

Any mismatch between manifest and archive content (missing file, extra file,
size mismatch, hash mismatch, kind mismatch) is `PKG_MANIFEST_MISMATCH`.

## 5. Scripts

Text scripts (`.sh`, `.py`, `.js`, and other interpreter-run text files) are
allowed but strictly governed. They are never rejected by extension alone,
and they are never trusted by presence alone.

Rules:

1. Every file under `scripts/**` MUST appear in `manifest.scripts[]` AND in
   `manifest.files[]` with `kind: "script"`. A script file not declared in
   `manifest.scripts[]` is `PKG_UNDECLARED_SCRIPT`.
2. Every `manifest.scripts[]` entry MUST also be declared in `skill.yaml`
   under `scripts:` (list of `{path, interpreter, purpose}`), so the human-
   readable spec and the machine manifest cannot drift.
3. Each script declaration MUST carry:
   - `path` — under `scripts/`
   - `interpreter` — e.g. `bash`, `sh`, `python3`, `node`
   - `purpose` — one of `install`, `runtime`, `helper`,
     `documentation_example`
   - `entry_point` — boolean; at most one `runtime` script may set it
   - optional `description`
4. Script files MUST be valid UTF-8 text and MUST NOT be binaries in disguise
   (§6).
5. Scripts with purpose `install` or `runtime` are elevated-risk: registries
   scan and surface them; ChengFlow subjects them to local execution policy
   and review. Purpose `documentation_example` scripts are never executed by
   tooling.
6. Archive executable bits on scripts are ignored. Local execution policy in
   ChengFlow decides whether and how a script may ever run.

## 6. Binary detection

Validators MUST reject, regardless of file extension or declared kind:

- ELF (`\x7fELF`), Mach-O (`0xFEEDFACE/0xFEEDFACF/0xCAFEBABE` + variants),
  PE (`MZ`), WebAssembly (`\0asm`)
- Java class files (`0xCAFEBABE` — overlaps Mach-O fat; both rejected)
- Python bytecode (`.pyc` magic), Lua bytecode (`\x1bLua`)
- shared libraries and static archives (`.so`, `.dylib`, `.dll`, `.a`, `!<arch>`)
- files declared as text/script whose leading bytes match any of the above
  (disguised binaries — `PKG_BINARY_FORBIDDEN`)

Reference files (`references/**`) may be non-UTF-8 (e.g. PNG diagrams) but
MUST still not match the binary-executable signatures above and MUST not be
nested archives.

## 7. Limits (archive-bomb defense)

Default hard limits; deployments may lower but not raise them for v1 publish:

| Limit                              | Default        |
| ---------------------------------- | -------------- |
| Max archive (compressed) size      | 20 MiB         |
| Max total expanded size            | 100 MiB        |
| Max single file expanded size      | 20 MiB         |
| Max file count                     | 512            |
| Max compression ratio (per file and total) | 200:1  |
| Max path length                    | 256 bytes      |
| Max path depth                     | 8 segments     |

Validators MUST compute SHA-256 and expanded sizes while streaming, and MUST
abort as soon as an *actual* limit is exceeded — declared (header) sizes are a
pre-check only and are never trusted (`PKG_EXPANDED_TOO_LARGE` /
`PKG_COMPRESSION_RATIO` / `PKG_TOO_MANY_FILES` / `PKG_FILE_TOO_LARGE`).

## 8. Compatibility fields

`compatibility.minimum_chengos_version` (required) and
`compatibility.maximum_chengos_version` (optional) bound the ChengOS engine
versions the skill supports. ChengFlow MUST refuse install (not merely warn)
when its own engine version is outside the declared range
(`PKG_ENGINE_INCOMPATIBLE`). The Registry stores and serves the range but
does not enforce it at download time.

## 9. Stable error codes

Both validators MUST emit these codes for the corresponding failures. Codes
are frozen; new failures get new codes.

| Code | Meaning |
| ---- | ------- |
| `PKG_MISSING_REQUIRED_FILE` | `SKILL.md`, `skill.yaml`, or `manifest.json` missing |
| `PKG_UNKNOWN_ROOT_ENTRY` | root file/dir outside the allowed set |
| `PKG_ABSOLUTE_PATH` | absolute path or drive letter in entry name |
| `PKG_PATH_TRAVERSAL` | `.`/`..` segment or separator confusion |
| `PKG_PATH_TOO_LONG` | path length/depth over limit |
| `PKG_DUPLICATE_PATH` | duplicate or Unicode/case-colliding paths |
| `PKG_SYMLINK_FORBIDDEN` | symlink entry |
| `PKG_HARDLINK_FORBIDDEN` | hardlink entry |
| `PKG_SPECIAL_FILE_FORBIDDEN` | device, FIFO, or socket entry |
| `PKG_NESTED_ARCHIVE` | nested archive file |
| `PKG_TOO_MANY_FILES` | file count over limit |
| `PKG_FILE_TOO_LARGE` | single file expanded size over limit |
| `PKG_EXPANDED_TOO_LARGE` | total expanded size over limit |
| `PKG_COMPRESSION_RATIO` | compression ratio over limit |
| `PKG_INVALID_UTF8` | required-text file is not valid UTF-8 |
| `PKG_INVALID_YAML` | `skill.yaml` fails to parse |
| `PKG_INVALID_JSON` | `manifest.json` / `workflow.json` fails to parse |
| `PKG_MANIFEST_INVALID` | manifest violates `manifest-v1.schema.json` |
| `PKG_MANIFEST_MISMATCH` | manifest ↔ archive inconsistency |
| `PKG_SLUG_MISMATCH` | slug differs between yaml/manifest/request |
| `PKG_VERSION_MISMATCH` | version differs between yaml/manifest/request |
| `PKG_INVALID_SEMVER` | version or compatibility bound is not SemVer |
| `PKG_INVALID_SLUG` | slug fails the slug rule |
| `PKG_UNDECLARED_SCRIPT` | script file not declared in manifest/skill.yaml |
| `PKG_SCRIPT_DECLARATION_INVALID` | declaration missing path/interpreter/purpose, or declares a missing file |
| `PKG_BINARY_FORBIDDEN` | native binary / disguised binary |
| `PKG_BYTECODE_FORBIDDEN` | bytecode artifact |
| `PKG_DEPENDENCIES_UNSUPPORTED` | non-empty `dependencies` in v1 |
| `PKG_ENGINE_INCOMPATIBLE` | local engine outside compatibility range (ChengFlow only) |
| `PKG_DIGEST_MISMATCH` | artifact bytes do not match the pinned digest |
| `PKG_FORBIDDEN_CONTENT` | embedded credentials/workspace/approval state |

Scan findings (secrets, risky content) are reported separately as scan
evidence with their own severity; they do not reuse `PKG_*` codes.

## 10. Fixtures

`fixtures/fixture-index.json` is the CI contract. Each fixture states how to
obtain the package bytes (a checked-in directory to be zipped, or a synthesis
recipe for hostile structures that cannot be represented on disk), which
validators must run it, and the exact expected outcome (`pass` or a list of
expected error codes). Both workspaces MUST run every fixture whose `targets`
include them and MUST fail CI on outcome drift. Schema or spec changes require
updating fixtures in the same change.
